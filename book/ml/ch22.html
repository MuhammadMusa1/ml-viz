Глава 22. Финальный проект: модель и интерфейс

Цель главы 🎯

После этой главы ты сможешь осмысленно улучшить модель с проверкой по кросс-валидации, выбрать правильную метрику, обернуть модель в веб-интерфейс и подготовить README.

Рабочий каркас есть. Теперь превращаем черновик в качественный продукт: улучшаем модель, честно её оцениваем, добавляем веб-интерфейс, который увидят другие, и пишем документацию. Это основная рабочая фаза проекта.

Улучшаем модель — но честно

Улучшение модели — это не «сделать число побольше любой ценой». Это осмысленные шаги, каждый из которых проверяется по кросс-валидации (глава 10), чтобы не обмануть себя случайным везением на одном разбиении.

  • Добавь или преобразуй признаки (feature engineering) — часто это даёт больше, чем смена модели. Новый осмысленный признак ценнее нового алгоритма.
  • Попробуй разные модели: лес, градиентный бустинг, регрессию — и сравни честно по кросс-валидации.
  • Подбери параметры через GridSearchCV, если данных немного и времени хватает.
  • Сравнивай каждый шаг с baseline и с предыдущей версией: стало реально лучше или это шум?

Внимание: осторожно с утечкой ⚠️

Улучшая модель, легко случайно устроить утечку данных (глава 6) — например, посчитать масштабирование или заполнение пропусков на всех данных до разделения. Держи ВСЕ преобразования внутри Pipeline: это и есть твоя автоматическая защита от утечки. Если вдруг точность подскочила до подозрительно высокой (0,99 там, где ждал 0,80) — первым делом ищи утечку, а не радуйся.

Выбери правильную метрику

Вспомни главу 11: accuracy подходит не всегда, особенно на несбалансированных данных. Задай себе вопрос, что дороже — ложная тревога или пропуск, — и выбери метрику под задачу (precision, recall, F1 или, для регрессии, MAE/MSE). На защите нужно будет объяснить, почему выбрана именно эта метрика, а не взята accuracy «по умолчанию». Осознанный выбор метрики — признак зрелого специалиста.

Оборачиваем в веб-интерфейс

Интерфейс делаем через Gradio (главы 16 и 20). Продумай, что пользователь вводит и что получает: текст → метка тональности, картинка → категория, числа → прогноз. Интерфейс должен быть понятен человеку, который ничего не знает о твоей модели, — например, твоей бабушке. Добавь понятные подписи к полям и короткое описание, что делает приложение.

# Запускать в Google Colab
import gradio as gr

def predict(user_input):
    # здесь вызываешь свой обученный pipeline
    result = pipe.predict([user_input])[0]
    return str(result)

demo = gr.Interface(
    fn=predict,
    inputs=gr.Textbox(label="Введите данные"),
    outputs=gr.Label(label="Результат модели"),
    title="Мой финальный проект",
    description="Кратко: что делает это приложение и как им пользоваться.",
)
demo.launch(share=True)

Готовим презентацию и README

Параллельно готовь два обязательных документа. Презентация — 3–5 слайдов для устной защиты на Demo Day. README — текстовое описание проекта, которое кладётся рядом с кодом (на GitHub или в Hugging Face Space). README — это «лицо» проекта в интернете: по нему незнакомый человек за минуту понимает, что ты сделал.

Что должно быть в README ℹ️

Название и одно предложение о том, что делает проект.

Задача: что предсказываем и зачем это нужно.

Данные: откуда взяты и что в них.

Как запустить: ссылка на живое приложение и краткая инструкция.

Результат: выбранная метрика и сравнение с baseline.

Задания

Базовый уровень

Улучши свою модель хотя бы одним осмысленным шагом (новый признак или другая модель) и проверь прирост по кросс-валидации. Оберни финальную модель в Gradio. Напиши README по пяти пунктам.

Со звёздочкой ⭐

Проведи полноценное сравнение 3+ моделей по кросс-валидации, обоснуй выбор метрики через цену ошибки и добавь feature importance в презентацию. Убедись, что все преобразования внутри Pipeline (защита от утечки).
