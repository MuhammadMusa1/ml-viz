Глава 35. Отдаём модель миру: FastAPI и мониторинг

Цель главы 🎯

После этой главы ты сможешь обернуть модель в API на FastAPI, объяснить разницу между интерфейсом для человека (Gradio) и API для программ, и понимать, зачем нужен мониторинг дрейфа данных.

В томе 1 мы отдавали модель людям через Gradio — красивый интерфейс с кнопками. Но в реальных системах к модели обращается не человек, а другие программы: сайт, мобильное приложение, другой сервис. Для этого модель оборачивают в API. FastAPI — современный стандарт для этого в Python.

Аналогия: витрина и служебное окно 💡

Gradio (том 1) — как витрина магазина для покупателей: красиво, с кнопками, для человека. API на FastAPI — как служебное окно приёма заказов, куда обращаются другие фирмы: без красоты, зато быстро, строго по формату, машина к машине. Одна модель может иметь и витрину (Gradio для демо), и служебное окно (API для интеграции в другие системы). В реальных продуктах модель почти всегда живёт за API.

Модель за API на FastAPI

FastAPI позволяет описать «эндпоинт» — адрес, куда программы шлют данные и получают ответ модели. Загружаем сохранённую модель (навык из фазы 1) и отдаём её предсказания по сети.

# pip install fastapi uvicorn
from fastapi import FastAPI
from pydantic import BaseModel
import joblib

app = FastAPI()
model = joblib.load("model.joblib")   # обученная модель (том 1 / фаза 1)

# Описываем, какие данные принимаем (проверка формата автоматом)
class Features(BaseModel):
    age: float
    income: float

@app.post("/predict")
def predict(data: Features):
    pred = model.predict([[data.age, data.income]])[0]
    return {"prediction": int(pred)}

# Запуск: uvicorn main:app --reload
# Программы шлют POST на /predict и получают JSON с ответом

Полезно знать ℹ️

FastAPI сам проверяет входные данные по описанию (класс Features): если пришло не то — вернёт понятную ошибку, а не упадёт. Ещё он автоматически создаёт страницу документации (адрес /docs), где можно потыкать API руками. Это делает FastAPI любимым инструментом для выпуска моделей. Связка полная: обучил модель (фаза 1) → сохранил (joblib/state_dict) → обернул в FastAPI → упаковал в Docker (глава 34) → выложил.

Мониторинг: модель незаметно стареет

Аналогия: карта устаревает 💡

Ты выложил модель — и на этом работа не кончается. Мир меняется: вкусы людей, цены, поведение. Данные, которые приходят модели сегодня, всё меньше похожи на те, на которых она училась. Это дрейф данных (data drift): модель незаметно «стареет» и предсказывает всё хуже, хотя её код не менялся, — как карта города, которая устаревает по мере стройки новых улиц. Без мониторинга ты этого не заметишь, пока не начнутся жалобы.

Что делает мониторинг: следит за двумя вещами. Первое — не «уехало» ли распределение входных данных (средний возраст клиентов вырос, появились новые категории). Второе — не падает ли качество модели на свежих данных. Если дрейф замечен — модель пора переобучить на новых данных. В серьёзных системах это делают автоматически и регулярно.

# Простейший детектор дрейфа: сравнить распределение "тогда" и "сейчас"
import numpy as np

def check_drift(train_values, new_values, threshold=0.2):
    # сравниваем средние (упрощённо; в проде — статтесты)
    drift = abs(new_values.mean() - train_values.mean()) / train_values.mean()
    if drift > threshold:
        print(f"ВНИМАНИЕ: дрейф {drift:.0%} — пора переобучить модель")
    else:
        print(f"OK: дрейф {drift:.0%}")
