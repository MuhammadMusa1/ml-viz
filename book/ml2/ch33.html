Глава 33. Командный Git: ветки, pull request, ревью

Цель главы 🎯

После этой главы ты сможешь работать с Git в команде: создавать ветки, оформлять pull request и проходить код-ревью — без хаоса и затирания чужой работы.

В томе 1 (и в приложении к нему) ты научился базовому Git — сохранять свой код на GitHub. Но настоящая сила Git раскрывается в команде: когда несколько человек пишут код одновременно и он не превращается в кашу. Это фундамент любой инженерной работы.

Аналогия: общий документ с черновиками 💡

Представь, что впятером пишете один документ. Если все правят один и тот же файл разом — хаос: перезаписываете друг друга, теряете куски. Git с ветками устроен умнее: каждый делает свою копию-черновик (ветку), спокойно работает в ней, а потом предлагает влить изменения в общий документ — но только после того, как остальные посмотрели и одобрили. Никто ничего не затирает, всё под контролем.

Ветки: своя песочница для каждого

Ветка (branch) — это отдельная линия разработки. Есть главная ветка main (рабочая, стабильная версия), а каждую новую задачу делают в своей ветке, не трогая main. Закончил — вливаешь обратно. Так сломанный код одного человека не ломает работу всех.

# Создать свою ветку под задачу и переключиться на неё
git checkout -b feature/add-model

# ... работаешь, коммитишь как обычно ...
git add .
git commit -m "Добавил модель классификации"

# Отправить свою ветку на GitHub
git push -u origin feature/add-model

Pull request и код-ревью

Аналогия: сдать работу на проверку 💡

Pull request (PR) — это предложение влить твою ветку в main, оформленное как заявка «посмотрите мою работу». Коллеги читают твои изменения, оставляют комментарии («тут лучше переименовать», «здесь возможна ошибка»), и только после одобрения код попадает в main. Это код-ревью — как сдать сочинение учителю на проверку перед тем, как оно пойдёт в общий сборник. Ловит ошибки до того, как они навредят, и все учатся у кода друг друга.

PR создают на сайте GitHub кнопкой (не в терминале): выбираешь свою ветку → «Create pull request» → описываешь, что сделал. Команда обсуждает, ты правишь по замечаниям, затем PR «мёржат» (вливают) в main. Так работают все IT-команды мира.

Как не создать хаос: правила команды

Командная гигиена Git ℹ️

Не коммить прямо в main — всегда через ветку и PR.

Одна ветка — одна задача. Не сваливай десять разных правок в один PR.

Понятные сообщения коммитов: «Исправил утечку данных в Pipeline», а не «фикс».

Регулярно подтягивай чужие изменения (git pull), чтобы твоя ветка не устарела.

Конфликт слияния (merge conflict) — это нормально: Git спросит, чью версию оставить, если двое правили одно место. Не паникуй, разбирай спокойно.

Задания

Базовый путь 🟢

Создай репозиторий на GitHub, заведи ветку feature/..., сделай в ней изменение, запушь и открой pull request на сайте. Опиши в PR, что изменил. Затем сам себе одобри и влей в main. Пройди весь цикл ветка → PR → merge.

Продвинутый путь 🔵

Вдвоём с товарищем (или с двух аккаунтов) поработайте над одним репозиторием: каждый в своей ветке правит РАЗНЫЕ файлы, делает PR, ревьюит PR другого с комментарием. Затем специально создайте конфликт (оба правите одну строку) и разрешите merge conflict вместе.
