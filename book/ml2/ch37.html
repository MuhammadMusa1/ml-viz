Глава 37. Надёжность: тестирование и CI/CD

Цель главы 🎯

После этой главы ты сможешь писать простые тесты для ML-кода через pytest и объяснить, как CI/CD (GitHub Actions) автоматически проверяет код при каждом изменении.

Как убедиться, что твоё изменение не сломало то, что работало вчера? Вручную перепроверять всё — нереально. Ответ индустрии: автоматические тесты (pytest) и автоматическая их проверка при каждом изменении (CI/CD). Это то, что делает командную разработку надёжной.

pytest: автоматическая проверка кода

Аналогия: контрольные точки 💡

Тесты — как контрольные точки в игре: если что-то сломалось, ты сразу видишь, где именно, и не проходишь весь уровень заново вслепую. Тест — это код, который проверяет другой код: «если подать вот это, должно получиться вот то». Изменил что-то — прогнал тесты — если все зелёные, ничего не сломал; если красный, сразу знаешь, что и где. Без тестов каждое изменение — риск втихую сломать то, что работало.

# pip install pytest
# файл test_model.py

def test_prediction_shape():
    # модель должна вернуть один ответ на один пример
    pred = model.predict([[25, 50000]])
    assert len(pred) == 1

def test_prediction_range():
    # для классификации ответ — из известных классов
    pred = model.predict([[25, 50000]])[0]
    assert pred in [0, 1]

def test_pipeline_no_crash_on_missing():
    # Pipeline должен пережить пропуск (у нас есть SimpleImputer)
    import numpy as np
    pred = pipeline.predict([[np.nan, 50000]])
    assert pred is not None

Что тестируют в ML

Полезно знать ℹ️

ML-код тестируют иначе, чем обычный. Проверяют: форму выхода (модель вернула сколько ожидали), диапазон (предсказания в разумных пределах), устойчивость (Pipeline не падает на пропусках/новых категориях), качество (точность на контрольном наборе не ниже порога). Тестируют не «правильность» каждого предсказания (модель имеет право ошибаться), а то, что система в целом ведёт себя ожидаемо и не деградировала.

CI/CD: робот-проверяющий

Аналогия: строгий, но неутомимый вахтёр 💡

CI/CD — это робот, который стоит на входе в main и проверяет каждое изменение. CI (Continuous Integration) — при каждом pull request автоматически прогоняет все тесты: не прошли — код не пустят в main. CD (Continuous Delivery) — если тесты прошли, автоматически выкатывает новую версию (например, пересобирает Docker и деплоит). Это неутомимый вахтёр, который никогда не забудет проверить и не пропустит сломанный код. Работает круглосуточно, без усталости.

На GitHub это делает GitHub Actions — ты кладёшь файл-инструкцию, и при каждом push/PR облако само прогоняет тесты. Файл простой: описываешь «на каждый push установи зависимости и запусти pytest».

# .github/workflows/tests.yml
name: Тесты
on: [push, pull_request]        # запускать при push и PR

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4          # взять код
      - uses: actions/setup-python@v5      # поставить Python
        with:
          python-version: "3.11"
      - run: pip install -r requirements.txt
      - run: pytest                        # прогнать тесты

Внимание ⚠️

CI/CD и GitHub Actions работают на GitHub, а тесты pytest можно писать и запускать где угодно, включая Colab. Для школ без глубокой инфраструктуры достаточно освоить pytest (писать тесты — универсальный навык), а CI/CD пройти на понимание: осознать, что робот прогоняет тесты автоматически при каждом изменении. Даже базовый набор тестов резко повышает надёжность командного проекта.
